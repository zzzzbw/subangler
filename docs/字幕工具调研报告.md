# 字幕自动化下载整理工具：技术方案与开源项目调研报告

> 调研时间：2026-11-21。范围：开源项目协议/技术栈、字幕源支持与命中率、部署形态、二次开发可行性。
> 数据说明：下载成功率没有行业统一公开指标，报告用「配额、反爬强度、匹配机制、社区反馈、可用基准」等可核实维度做相对评估，不虚构精确百分比。

---

## 0. 结论速览（TL;DR）

1. **没有单一项目同时满足「MIT + 活跃维护 + 多平台 + Web 交互 + Docker 一键部署」。** 最务实的路线是：
   - **以 Subliminal（MIT、活跃、Provider 插件化）作为下载/匹配内核**；
   - 自研一层 Provider 适配层 + Web UI/API + 任务队列；
   - 中文源按配置接入 ASSRT / SubDL / Zimuku / SubHD 等，并默认走「多源回退」。
2. **如果目标是先跑起来用**：直接部署 Bazarr（GPL-3.0，Docker 成熟、60+ Provider、交互最好），但它依赖 Sonarr/Radarr，且 GPL 会约束对外分发修改版。
3. **如果中文内容是主场景且能接受一定风险**：可基于 ChineseSubFinder 的 MIT fork（如 wolfyax）改造；但原仓停更、且已移除部分字幕站的直接抓取，长期可维护性不如 Subliminal。
4. **成功率瓶颈在 Provider，不在下载器本身**：OpenSubtitles 免费账号 20 次/天、匿名 5 次/天；SubDL 免费约 50 次下载/天；中文站普遍有验证码/域名漂移；Subscene 已于 2024-05 关闭。必须做多源优先级、配额感知、熔断降级的回退链。
5. **交互优化的重点**：手动挑选、失败原因可视化、配额看板、Provider 一键启停、字幕预览与轴校正预览、进度/队列 SSE 推送——这些在 Bazarr 与 Subtitle Scout 上有成熟范式可抄。
6. **部署**：Bazarr / Subliminal / ChineseSubFinder / Subtitle Scout / Lingarr 均有 Docker 镜像或 Compose；从 0 自研建议直接产出 Compose，避免依赖宿主机非容器化组件（MediaInfo / unrar 需特别处理）。

### 2.2 难度对比（以「单体服务 + Web UI + 5 个 Provider + Docker」为同一交付边界，粗估）

| 工作项 | 基于 Subliminal 二开 | 基于 ChineseSubFinder fork | 从 0 到 1 |
|---|---|---|---|

| Docker/Compose/CI | 0.5 人周 | 已有镜像，0.5 人周 | 1 人周 |

> 数字是同一功能边界下的工程估算，不是实测工时；差异主要来自「是否已有 Web UI/队列/Provider 框架」。若只要 CLI 工具，Subliminal 几乎开箱即用（1 人周内）。

### 2.3 关键判断

- **Subliminal 是唯一「MIT + 活跃 + 插件化 + 可作为库嵌入」的组合**，适合作为长期可维护内核；它的缺口（UI、队列、轴校正）恰好是你可以按交互目标定制的部分，而不是需要推翻重写的核心。
- **ChineseSubFinder 的优势是现成中文 Web 产品，劣势是站点能力被主动削弱**；如果你要「后续可维护性」，不建议把核心押在一个已停更上游 + 多个分裂 fork 上。
- **从 0 到 1 的唯一优势是架构纯净**：若团队对可维护性要求极高且资源充足，可直接按「Provider 插件 + 领域事件 + 可观测性」设计，但前 1–2 个月基本是在重造 Subliminal 已有的轮子。
- **许可证策略建议**：内核/自研层保持 MIT；若引入 FlareSolverr（MIT）做 Cloudflare 绕过可安全嵌入；避免把 AGPL 的 Lingarr/Subtitle Scout 代码复制进闭源产品。

### 3.2 成功率：可核实的结论

**不存在统一的「下载成功率」公开基准**。不同工具/语言/库类型的差异极大。可核实的判断依据：

1. **匹配方式决定上限**：OpenSubtitles 的 movie hash（取文件首尾 64 KB）能锁定同一发行版，命中即几乎必然对轴；文件名解析（guessit）匹配是次优；纯标题搜索最差。Bazarr 明确支持「跳过 hash 计算」但会牺牲匹配质量。
2. **配额是最大的工程性失败源**：免费 OS 账号 20 次/天意味着 30 集剧需要 2 天；社区常见报错 `429 Too Many Requests` / `All providers are throttled`，Bazarr 会把触发限流的 Provider 冷却 1–3 小时。SubDL 免费 50 次/天明显更适合批量。
3. **反爬成本可量化但不稳定**：FlareSolverr（MIT）在 2026 年一项 8 工具基准中 JS 挑战绕过率 **90.38%**、平均 **15.21 秒**，但**不能解交互式 CAPTCHA**；且 2025–2026 Cloudflare 逐步升级挑战类型。中文站验证码需 OCR 或第三方打码服务，属于持续维护负担。
4. **站点生命周期风险真实存在**：Subscene 关闭、ChineseSubFinder 主动下线部分站点、Zimuku/SubHD 域名频繁变更，任何「硬编码站点 URL」的设计都会在几个月内失效。
5. **"下载到" ≠ "可用"**：不同发行版帧率/剪辑不同会导致轴偏移；Bazarr 提供 ffsubsync 自动对齐（可按视频音轨或内嵌字幕为参考），这是提升「有效成功率」最划算的一环。Subtitle Scout 进一步做「下载前对照视频校验 + LLM 甄别 + 宁缺毋滥」。

### 3.3 快速切换平台的设计模式（建议直接采用）

```
ProviderAdapter (接口)
  ├─ capabilities: languages, content_types, requires_auth, quota
  ├─ search(video_meta, language) -> Candidate[]
  ├─ download(candidate) -> SubtitleFile
  └─ health(): OK | THROTTLED | BROKEN
```

- **注册表 + 配置驱动**：每个源一个 Adapter，通过配置启用/禁用、设优先级、填凭证；新增源不改核心代码。Subliminal 的 `entry point`、SubFinder 的 `--api_urls`、Bazarr 的「Enabled Providers / 并行搜索」都是现成范式。
- **回退链**：hash 精确匹配 → 发行名评分匹配 → 下一个 Provider → 人工上传 → Whisper ASR 兜底 → Lingarr 翻译补齐。给每层设最低分阈值，宁缺毋滥。
- **配额感知调度**：监控响应里的剩余额度/重置时间（OS 返回 `remaining` / `reset_time`），本地记账，配额耗尽自动跳过该源；请求间隔限速（Sub-Zero 自行对 ASSRT 保守限速 5 次/分钟；ASSRT 官方配额实为 20 次/分钟，见 M2 官方文档核实）。
- **熔断与冷却**：某源连续 N 次 4xx/5xx 或触发限流 → 标记 THROTTLED，冷却 1–3 小时，避免每次搜索都撞墙。
- **并行 vs 串行可切**：Bazarr 支持「同时搜索所有启用的 Provider」（快但耗资源），低配设备/NAS 建议串行。
- **站点地址外置**：域名、搜索路径、下载 API 路径全部放配置/数据库，不写死在代码里（SubFinder 的 `api_urls` 是正面案例）。

## 4. 部署难度

| 项目 | 部署方式 | 关键依赖 | 难度 | 坑 |
|---|---|---|---|---|
| **Bazarr** | `lscr.io/linuxserver/bazarr:latest`，Compose 两卷（config + media） | 必须先有 Sonarr/Radarr | ⭐ | **默认无登录鉴权**，公网暴露前必须设用户名密码；容器路径需与 Sonarr/Radarr 一致；PUID/PGID；ffsubsync 时内存突增 |
| **Subliminal** | `pipx install subliminal` 或 `ghcr.io/diaoul/subliminal` | Python ≥3.10；建议装 MediaInfo（pip 不自动装） | ⭐⭐ | 无 Web/队列，需要自己包一层；`BUILD_WITH_UNRAR=true` 时 unrar 许可问题 |
| **ChineseSubFinder** | Docker Hub `allanpk716/chinesesubfinder`（latest / latest-lite），需指定具体 tag | 目录命名/刮削器规范 | ⭐⭐⭐ | 国内镜像源 latest 可能非最新；CGO 编译复杂；站点直抓能力已削弱 |
| **SubFinder** | pip / 源码 | unrar（Linux/macOS 自装） | ⭐⭐ | 无官方 Docker；老旧 Python 依赖 |
| **Subtitle Scout** | `docker compose up -d` + GHCR 镜像；8099 端口 | TMDB API + OpenAI-compatible LLM | ⭐⭐⭐ | 默认挂载宿主机根目录权限高；无内建 HTTPS；大陆 TMDB 直连常被墙；AGPL 限制 |
| **Lingarr** | Compose（GHCR/Docker Hub，amd64+arm64）；9876 端口 | 翻译服务（可本地 Ollama/LibreTranslate） | ⭐⭐ | 默认 MySQL，可换 SQLite 简化；DB healthcheck + depends_on；`MAX_CONCURRENT_JOBS=1` 起步 |
| **subbuzz** | Jellyfin 插件仓库 URL / Emby dll | Jellyfin 10.8–10.11 对应构建 | ⭐ | 需匹配服务器大版本；只支持 opensubtitles.com |

**自研部署建议**：单容器 Compose（FastAPI/Node + SQLite + 前端静态资源），媒体目录只读挂载、字幕写回同目录；把代理、FlareSolverr、打码服务做成可选 sidecar；默认带鉴权与反代示例；提供 `doctor` 自检命令（参考 Subtitle Scout）。

## 5. 针对你三个关注点的落地建议

### 5.1 可维护性

- **内核与外壳分离**：`subtitle-core`（扫描、评分、Provider 接口、落盘）保持 MIT 且无 UI 依赖；`web`/`worker` 独立演进。这是 Subliminal 的最大价值。
- **Provider 全部插件化**：配置即能力，热启停；站点 URL/凭证不进代码仓库。
- **可观测性**：每次搜索记录「候选项、评分、选择理由、失败原因、配额余量」，这既是调试工具，也是交互层的「为什么没下到」解释。
- **自动化测试**：用固定视频样本 + mock Provider 响应做回归；站点 HTML 解析用快照测试，域名变更时先失败在测试而不是线上。

### 5.2 下载成功率

- 默认启用 ≥3 个源（OS.com + SubDL + ASSRT，中文场景再加 Zimuku/SubHD 作为可选项）。
- hash 优先、评分阈值可调；**自动 ffsubsync 对齐默认开启**（大文件注意内存）。
- 配额记账 + 限速 + 熔断；失败自动降级到下一个源，最终落 Whisper/翻译兜底。
- 把「反爬」当可选项：FlareSolverr sidecar（MIT）应对 JS 挑战；交互式验证码交给用户手动或第三方打码，不内置破解逻辑。
- 定期（如每周）跑一次 Provider 健康检查并在 UI 标红失效源。

### 5.3 交互优化（可直接抄的范式）

- **Bazarr**：手动搜索/选择、语言 Profile（按剧/按电影）、升级规则、历史与黑名单、并行搜索开关、Whisper 兜底、轴校正阈值、后处理脚本。
- **Subtitle Scout**：设置向导、SSE 实时状态、Activity/决策历史、工具调用 trace、fail-closed（没有足够好的就不装）、`doctor` 自检、realign 可回滚。
- **建议最小集**：任务队列 + 实时进度、失败原因可读文案（配额耗尽/验证码/无匹配/版本不符）、Provider 开关与优先级拖拽、配额看板、手动挑选与预览、下载后轴校正预览、通知（Webhook/Telegram）。

## 6. 合规与风险

- **许可证**：GPL（Bazarr/subbuzz）内部自用无义务，分发修改版需开源；AGPL（Lingarr/Subtitle Scout）网络服务也触发开源义务；MIT（Subliminal/ChineseSubFinder/SubFinder/SubPlz/FlareSolverr）最宽松，但注意 Subliminal+unrar 的独立许可。
- **内容版权**：字幕内容本身不受软件许可证覆盖。OpenSubtitles、SubDL、ASSRT、SubHD、Zimuku 等各有服务条款、账号与配额限制；商用或大规模拉取前需逐站核对，建议只做个人/家庭自用的技术验证。
- **安全**：字幕站压缩包可能夹带恶意文件；下载后做文件类型校验与解压路径检查（zip-slip）；不要以 root 运行容器；公网暴露必须加鉴权与 HTTPS。
