# 字幕自动化下载整理工具 — 详细设计方案

> 版本：v0.3 · 2026-11-21（全部关键决策已确认）
> 定位：以 Subliminal（MIT）为下载/匹配内核，自研调度层、Provider 适配层、Web UI/API 与可观测性。
> 目标：可维护性 > 下载成功率 > 交互体验（按调研报告的三个关注点排序）。

**已确认决策**
| 决策项 | 结论 | 对架构的影响 |
|---|---|---|
| 使用形态 | **NAS / Docker 常驻** | 强制鉴权 + 反代、7x24 定时扫描、Worker 常驻、PUID/PGID 与路径映射成为必选项 |
| Provider 范围 | **中英兼顾**：OS.com + SubDL + ASSRT + Zimuku | 首版就要自写 2 个中文 Provider + 快照测试，工时增加约 1–2 人周 |
| 前端栈 | **React + TypeScript** | 拖拽排序、SSE、候选对比用成熟组件，前端约 2–3 人周 |
| 轴对齐 | **暂不做，列为待办** | 从 M1/M2 移出，不引入 ffsubsync/ffmpeg 依赖（保留 postprocess 扩展点） |
| 凭证/路径配置 | **全部做成配置项，页面可设置** | 新增「配置中心」：API Key、token、媒体库路径、Provider 参数均在 UI 维护，凭证加密落库；改配置免重启 |
| Whisper 兜底 | **不需要** | 回退链终止于人工挑选/上传，移除 Whisper sidecar 与相关依赖 |
| 数据库 | **SQLite** | WAL 模式，单容器足够；不引入 PostgreSQL/Redis |

---

## 0. 设计原则（先定边界，再写代码）

| 原则 | 具体含义 | 违反的后果 |
|---|---|---|
| 内核与产品分离 | `sub-core` 只依赖 subliminal，无 Web/队列依赖；`sub-api`/`sub-worker`/`sub-ui` 独立演进 | 上游升级即全量回归 |
| 配置即能力 | Provider 的启停、优先级、凭证、站点 URL、限速全在配置/DB，不进代码 | 站点漂移就要发版 |
| 每次决策可解释 | 每次搜索保存候选、评分、选择/放弃理由、配额余量、耗时 | "为什么没下到"无法回答 |
| 失败必须降级 | 任一 Provider 失败不中断任务，自动走回退链，最终落到人工/ASR | 单点失败导致整季缺字幕 |
| 宁缺毋滥 | 评分低于阈值不落盘，交给人工挑选 | 装错轴的字幕比没有更糟 |

---

## 1. 总体架构与进程模型

四层：交互层（Web UI / REST API / SSE）→ 应用层（任务队列 / 配额调度 / 回退链 / 决策日志）→ 领域核心（Subliminal 内核 + Provider 适配层）→ 基础设施（SQLite / ffsubsync / 可选 sidecar）。

**进程模型（NAS / Docker 常驻，单容器多进程）**：
- `sub-api`：FastAPI，提供 REST + SSE，负责鉴权与配置管理。
- `sub-worker`：独立进程，跑扫描/下载任务，消费任务队列。API 与 Worker 解耦，Worker 崩溃不影响 UI。
- `sub-scheduler`：常驻定时器，按各媒体库的 `scan_cron` 触发扫描与 `retry_failed`，错过窗口补跑一次。
- `sub-ui`：构建期产出静态资源，由 API 托管单端口，避免 CORS 与双容器。
- 队列与状态落 SQLite（WAL 模式，`busy_timeout`）。NAS 单用户场景下 SQLite 足够，不需要 Redis；若日后多实例再把队列表替换为 Redis/ARQ，**任务接口不变**。
- **鉴权是必选项**：默认开启用户名密码登录（bcrypt/argon2 哈希 + HttpOnly cookie），反代只暴露 HTTPS；API 与 SSE 全部走鉴权中间件。
- **路径映射**：容器内统一挂到 `/media`，媒体目录按需读写（字幕写回同目录），PUID/PGID 对齐 NAS 用户，避免权限问题。

```
[浏览器] --HTTP/SSE--> [sub-api:8000] --任务表--> [sub-worker]
                          |                        |
                          +------ SQLite ----------+
                                                   |
                                      [sub-core: subliminal]
                                                   |
                              [OS.com | SubDL | ASSRT | Zimuku | ...]
```

## 2. Subliminal 复用边界（最关键的技术决策）

**结论：复用 Subliminal 的"数据结构与算法"，不复用它的"编排流程"。**

| 复用 | 不复用 | 原因 |
|---|---|---|
| `scan_videos()` 递归扫描 | `download_best_subtitles()` 的一次性编排 | 后者是"搜完即下载"，插入不了配额检查、熔断、人工挑选、降级 |
| `Video` / `Subtitle` 数据模型、`compute_score()` | 它内置的 Provider 选择循环 | 回退链、并行/串行、优先级需要自己控制 |
| `save_subtitles()` 命名落盘 | — | 成熟且正确，直接复用 |
| `region` + dogpile.cache | — | 缓存 search 结果，降低配额消耗 |
| guessit / knowit / refiners（hash、metadata、tmdb/tvdb、external_subtitles） | — | 文件名解析与 hash 匹配是命中率基石；建议配置 TMDB key 启用 tmdb refiner，补全标题/年份/集数元数据，提升非 hash 搜索的评分质量 |

具体做法：自建 `DownloadOrchestrator`，编排流程为
`scan → refine → candidates = [p.search(...) for p in providers] → score → 阈值判定 → download → postprocess → save`。

**代价**：要自己维护一份"Subliminal 版本适配层"（约 100–200 行），把 `Video`/`Subtitle`/`score` 的调用集中在一处。上游升级只改这一处。这是为可维护性付的小额保险费。

**上游演进风险（2026-11-21 核实）**：main 分支已完成 Provider/Refiner 异步化改造（PR #1395，2026-10 合并；opensubtitlescom 已于 2026-11 转为 AsyncProvider，依赖新增 aiohttp/aiofiles），最低 Python 已升至 ≥3.11（PyPI 2.8.0 仍为 ≥3.10，与调研报告标注一致）。对策：① 依赖锁定 `subliminal==2.8.x`，升级视为契约测试事件；② 自建 `ProviderAdapter` 接口**直接定义为 `async def search/download`**，原生同步 Provider 用 `anyio.to_thread` 包装——未来上游全面异步化时只改适配层，不动调度层。

**二次开发方式**：`pip install subliminal==2.8.x` 作为依赖，不改上游源码；自建 Provider 通过 `entry_points` 注册到 `subliminal.providers` 组，或直接由自己的 Adapter 注册表管理（推荐后者，可控性更强）。

## 3. Provider 适配层

### 3.1 统一接口

```python
class ProviderAdapter(Protocol):
    name: str                       # 唯一标识，如 "opensubtitles_com"
    display_name: str
    capabilities: Capabilities      # languages, content_types, requires_auth, hash_support

    async def search(self, video: Video, language: Language) -> list[Candidate]: ...
    async def download(self, candidate: Candidate) -> SubtitleFile: ...
    def health(self) -> HealthState: ...        # OK | THROTTLED | BROKEN | DISABLED
    def quota(self) -> QuotaState: ...          # remaining, reset_at, source
```

`Candidate` 是统一候选结构：`provider / external_id / language / release_name / fps / hearing_impaired / score_breakdown / download_url / size`。评分细项保留，供 UI 解释"为什么选它"。

### 3.2 两种 Provider 来源

1. **包装 Subliminal 原生 Provider**（2.8.0 实际为 12 个 entry point：addic7ed、bsplayer、gestdown、napiprojekt、opensubtitles（.org 旧接口）、opensubtitlesvip、opensubtitlescom、opensubtitlescomvip、podnapisi、subtis、subtitulamos、tvsubtitles）：写一个 `SubliminalProviderAdapter` 通用包装器，把原生 provider 的 `search/download` 接进来，外层统一插桩计数、限速、熔断。注意：**SubDL 不是 Subliminal 原生 Provider（已核实 2.8.0 与 main 的 provider 目录均无 subdl 模块），需自建**（见下）。addic7ed 上游建议以 gestdown（无 reCAPTCHA）替代；opensubtitles（.org 旧接口）仅作遗留兜底。原生 Provider 清单随版本变化，启动时经 `subliminal.providers` entry point 组自动发现并列出，UI 里勾选启用。
2. **自建 Provider（首版必做，中英兼顾已确认）**：
   - **ASSRT**：官方 token + API，限速 **20 次/分钟**（官方文档核实，token 与 IP 共享配额），中文覆盖最厚，作为中文首选源。
   - **SubDL**：**非 Subliminal 原生，需自建**（已核实）；官方 REST API，免费约 50 次下载/天，承接 Subscene 归档，作为英文主力源之一。有官方 API，比 HTML 抓取类简单，粗估 2–4 人天。
   - **Zimuku**：HTML 抓取 + 域名外置配置，需 FlareSolverr 应对 JS 挑战；验证码场景转人工，不做自动打码。
   - 三者放 `providers/custom/`，各自带 `fixtures/` 快照测试；站点改版先测试红再修解析。高风险源默认关闭，UI 可一键启用。
   - SubHD 因 2026-05 大规模下架 + 腾讯验证码，首版不做，列为观察项。

### 3.3 配额与熔断（成功率的核心工程）

- **本地记账**：每次 `search`/`download` 前后读写 `quota_ledger` 表；解析响应头/JSON 中的 `remaining` 与 `reset_time`（OS.com 有返回）。免费账号 20 次/天、SubDL 50 次/天，记账后 UI 直接显示"今天还能下几个"。
- **限速**：按 Provider 独立令牌桶，ASSRT 设 20 次/分钟（官方文档值，可配置下调）；并发下载数按 Provider 限流（默认 2）。
- **熔断**：连续 N 次（默认 3）超时/429/5xx → `THROTTLED`，冷却 1–3 小时；冷却期内调度器直接跳过，不撞墙。定时探活恢复。
- **站点 URL 外置**：域名、搜索路径、下载路径全部存 `provider_config.endpoints`（JSON），域名字段可在 UI 修改，应对 Zimuku/SubHD 漂移。

### 3.4 并行 vs 串行

配置 `search_mode = parallel | sequential`。并行快但耗配额与资源；NAS/低配设备用串行。默认并行 3 个源，可设上限。

## 4. 领域模型与数据库表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `media_library` | id, root_path, name, scan_cron, enabled | 媒体库根目录（可多个） |
| `video` | id, library_id, path, title, year, season, episode, video_hash, fps, embedded_langs, status | 扫描结果，唯一键 path |
| `subtitle` | id, video_id, language, path, provider, hash, score, is_manual, created_at | 已落盘字幕；去重靠 (video_id, language, hash) |
| `job` | id, type, payload_json, state, progress, error_code, created_at, finished_at | 任务队列与历史 |
| `provider_config` | name, enabled, priority, credentials_ref, endpoints_json, rate_limit, min_score | Provider 配置（凭证加密或引用环境变量） |
| `quota_ledger` | provider, day, action, count, remaining, reset_at | 配额记账与看板 |
| `decision_log` | job_id, video_id, step, provider, candidate_json, score, reason, latency_ms | 可观测性核心 |
| `user` / `session` | 用户名、密码哈希、token | 鉴权（公网暴露必须有） |
| `app_config` | key, value_json, value_type, sensitive, updated_at | 全局配置项（页面可改，见 4.1） |
| `config_audit` | key, old_value, new_value, operator, changed_at | 配置变更审计（敏感值只记"已修改"） |

**落盘命名**：复用 `save_subtitles()` 默认规则 `<视频名>.<语言码>.srt`；配置可选 `single=True` 合并双语。已有字幕（含内嵌轨）检测在扫描阶段完成，直接标记 `status=has_subtitle` 跳过，避免重复下载（这正是上次 E04/E06/E07/E08 的情况）。

### 4.1 配置中心（本次确认：所有配置页面可设）

**设计目标**：凭证、路径、Provider 参数、调度策略全部页面可改，改完即时生效，免重启、免改 Compose/环境变量；每次修改留审计。

**配置分层与优先级**（高覆盖低）：
```
默认值(代码内置) < app_config(数据库/页面) < 环境变量(仅用于首次引导)
```
- 环境变量只用来注入"首次启动的引导值"（如初始管理员账号），一旦数据库中存在对应 key，以数据库为准。
- 所有配置读写入口统一走 `ConfigStore.get(key) / set(key, value)`，禁止业务代码直接读 `os.environ` 或写死常量。

**配置项清单（全部页面可设）**：

| 分组 | 配置项 | 类型 | 敏感 |
|---|---|---|---|
| 通用 | 默认语言偏好、下载并发数、搜索模式(并行/串行)、日志级别 | 混合 | 否 |
| 媒体库 | 根目录路径、扫描 cron、扫描深度、排除规则 | 字符串/数组 | 否 |
| Provider | 每个源的启用/禁用、优先级、最小评分阈值、超时、限速、站点 endpoints URL | 混合 | 部分 |
| 凭证 | OS.com API Key + 账号密码、ASSRT token、Zimuku cookies | 字符串 | **是** |
| 落盘 | 命名规则、单/双语合并、已有字幕跳过策略 | 混合 | 否 |
| 安全 | 会话时长、是否允许注册、反代可信网段 | 混合 | 否 |
| 通知（可选） | Webhook/Telegram 地址 | 字符串 | 是 |

**敏感配置安全**：
- 凭证类（API Key / token / cookie / 密码）用 **Fernet 对称加密**落 `app_config`，密钥由首次启动生成并保存到 `config/secret.key`（权限 600，不进 git）；UI 只显示掩码 `sk-****3f2a`，并提供"显示/隐藏"切换。
- `config_audit` 对敏感 key 只记录"于何时被谁修改"，不记录明文旧值/新值。
- 配置导出/备份时对敏感项脱敏；导入时不覆盖已有凭证（避免误把空值写进去）。

**即时生效机制**：
- 非连接型配置（阈值、并发、路径、cron）修改后写 DB 并广播配置版本 `config_version++`；Worker/Scheduler 在每个任务开始时读取最新版本，无需重启。
- 连接型配置（凭证、Provider endpoints）修改后触发该 Provider 实例重建 + 一次 `health()` 探活，页面即时显示"连接成功/失败"。
- 提供"测试连接"按钮：保存前用当前填写的凭证跑一次最小请求，避免存了错值。

**API 设计（补充）**：
```
GET    /api/config                     全量配置（敏感项掩码）
GET    /api/config/{key}               单项
PATCH  /api/config                     批量更新 {key: value, ...}，写审计
POST   /api/config/test-connection     用传入凭证测试 Provider 连通性
GET    /api/config/audit               变更历史
POST   /api/config/export              导出（脱敏）
```

**Settings UI 页面**：左侧分组导航（通用 / 媒体库 / 字幕源 / 凭证 / 落盘 / 安全），右侧表单；凭证项用密码框 + 显隐切换 + 测试连接按钮；底部"未保存更改"提示与保存/重置；改动后顶部提示"已生效，无需重启"。

## 5. 任务队列与回退链

### 5.1 任务类型
`scan_library` / `download_video` / `download_batch` / `sync_subtitle` / `health_check` / `retry_failed`。

### 5.2 状态机
`PENDING → QUEUED → RUNNING → (SUCCESS | PARTIAL | FAILED | SKIPPED)`。
`PARTIAL` 表示多语言里只拿到部分——UI 明确显示缺哪种，`retry_failed` 只重试缺失语言。

### 5.3 回退链（每集的执行顺序）
1. 已有字幕/内嵌轨检测 → 有则跳过。
2. `video_hash` 精确匹配（OS.com 等支持 hash 的源）。命中即对轴，优先级最高。
3. 文件名 + 元数据评分搜索，多源并行（OS.com + SubDL + ASSRT + Zimuku），取分数最高且 ≥ 阈值者。
4. 中文源与英文源**独立记账、独立回退**：中文字幕首选 ASSRT/Zimuku，英文首选 OS.com/SubDL；某一语言失败不影响另一语言落盘。
5. 阈值不达标 → 不落盘，进入"待人工挑选"列表，UI 展示候选 + 评分 + 在线预览。
6. 全部源失败/配额耗尽 → 标记 `needs_attention` + 可读失败原因，进入人工挑选/上传流程（**不做 Whisper 兜底，已确认**）；可选发通知提醒用户。
7. **轴对齐暂不纳入**（已确认待办）：`postprocess` 保留扩展点，落盘后留下钩子，未来接 ffsubsync 不改主流程。

### 5.4 幂等与重试
每个 `download_video` 任务带 `idempotency_key = (video_id, language, provider_set_version)`；重跑不重复落盘。失败重试指数退避，最多 3 次；熔断状态跳过不计入重试次数。

## 6. REST API / SSE 设计（示例）

```
POST   /api/libraries                     新增媒体库
POST   /api/libraries/{id}/scan           触发扫描
GET    /api/videos?library=&status=&lang= 字幕状态列表（筛选"缺字幕"）
POST   /api/jobs/download                 批量下载 {video_ids, languages, provider_names?}
GET    /api/jobs/{id}                     任务详情
GET    /api/jobs/{id}/events              SSE 实时进度
GET    /api/jobs/{id}/decisions            决策日志（解释为什么没下到）
GET    /api/candidates?video_id=&lang=    候选列表（人工挑选）
POST   /api/candidates/{id}/install       安装选中的候选（可带轴校正参数）
GET    /api/providers                     源状态：启停/优先级/健康/配额
PATCH  /api/providers/{name}              改配置、启停、拖动优先级
GET    /api/config                        全量配置（敏感项掩码）
PATCH  /api/config                        批量更新配置（页面设置入口）
POST   /api/config/test-connection        测试 Provider 凭证连通性
GET    /api/config/audit                  配置变更历史
GET    /api/health                        doctor 自检：依赖/权限/网络/凭证
POST   /api/auth/login                    登录
```

SSE 事件类型：`job.progress` / `job.step` / `job.done` / `provider.throttled` / `quota.low`。前端订阅后无需轮询。

## 7. Web UI 页面与交互优化

| 页面 | 核心内容 | 解决的痛点 |
|---|---|---|
| 总览 Dashboard | 缺字幕数量、成功率趋势、配额余量、失败原因分布 | 一屏掌握状态 |
| 媒体库/剧集视图 | 树状目录 + 每集语言徽标（有/缺/人工/内嵌），筛选"仅看缺字幕" | 快速定位缺口 |

## 11. 部署方案（NAS / Docker 常驻，已确认）

**单容器多进程 + Compose**（推荐）：
```
Dockerfile: 多阶段构建，python:3.12-slim + ffmpeg/ffprobe + mediainfo
            （首版不装 ffsubsync；前端在构建期 npm build，产物由 API 托管）
docker-compose.yml:
  sub-angler:
    image: 自建
    ports: ["8765:8765"]
    volumes:
      - ./config:/app/config            # SQLite + 配置 + 凭证引用
      - /volume1/tvshows:/media/tvshows:rw   # NAS 路径，字幕写回同目录
    environment: [PUID, PGID, TZ, UMASK, SUBLIMINAL_API_KEY, ASSRT_TOKEN, ...]
    restart: unless-stopped
    healthcheck: /api/health
```
- 媒体目录**必须可写**（字幕写回同目录）；PUID/PGID 对齐 NAS 媒体库属主，避免写回失败。
- **可选 sidecar**：仅 `flaresolverr`（Zimuku 的 JS 挑战，建议启用）；Compose 中注释掉，按需开启。**不部署 Whisper**（已确认不需要）。
- **鉴权默认开启**，无跳过选项；随仓库提供 Nginx/Synology 反代 + HTTPS 示例。
- 首次启动跑 `doctor`：检查媒体目录读写、依赖、Provider 网络与凭证，输出可读报告。
